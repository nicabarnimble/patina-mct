# Children and Vision after NIC-63 / PR #108

## Recommendation and evidence boundary

Doug wants useful applications assembled from Children, and Mothers that can cooperate across personal, other-owner, and shared groups. **Recommendation:** start with small WIT-only, bounded read/compute Children. Model ownership, Vision membership, permission to call, and Toy authority separately. Do not make every Mother share one credential or relabel every group as one Vision.

This is planning only, inspected on `nicabar` at `bc48d1e0d721d1531a58192a69ef65ffd234882f`. No source changes, builds, runtime tests, commits, deployments, or branch changes were performed. The only requested deliverable is this file. Statements marked **proposed** are recommendations, not shipped contracts. Test citations describe source assertions or recorded historical evidence, not tests rerun during this consultation.

The architectural baseline is a sovereign Mother per deployable node, local WASM-component Children identified by WIT operations, and explicit Toy authority. Vision is a sharing boundary, not necessarily a tenant or owner. [Source: `layer/core/what-is-mct.md`, “The name is the ontology”, “The core inversion”, “Vision”.]

# B. Canonical Child proposal

## 1. Contract and lifecycle

**Proposed:** make the default Child a bounded application operation, not a miniature daemon. A reference package should contain the component, `child.toml`, its versioned WIT and dependencies, provenance/integrity material, example input/output, and one allow/deny integration test. Use `mct-repo-report` as the starting point rather than inheriting the broad Slate or watcher worlds. The existing loader and fixture packaging already distinguish component integrity from authority. [Basis: `crates/mct-repo-report/{child.toml,wit/world.wit}`; `crates/mct-daemon/tests/fixtures/mct-test-echo-0.1.0/PROVENANCE.md`; `crates/mct-kernel/src/artifact.rs`.]

**Proposed world profiles, not three new runtimes:**

- **Pure compute.** One versioned domain interface, typed request/result, no Toy imports. A diff, ranker, validator or reducer fits here. The typed-record fixture demonstrates record lowering/lifting today. [Basis: `crates/mct-daemon/src/wasm.rs`, `typed_record_component_path`.]
- **Read/compute.** The same domain interface plus exact WASI filesystem 0.2.3 types/preopens. Keep `/project` read-only and content-address inputs. This is the smallest proven useful profile. [Basis: `crates/mct-repo-report/wit/world.wit`; `crates/mct-daemon/src/daemon/resident/execution.rs`, `resident_directory_read_host_adapters`; `docs/nic63-mesh-job.md`.]
- **Stateful/event component, opt-in.** Import only the state/event capabilities actually required. Keep business control/events separate from optional compatibility lifecycle hooks. Do not prescribe a universal “all Toys” world. Current keyvalue/messaging wiring is Watch-specific and needs deliberate generalization before advertising this as a generic profile. [Basis: `crates/mct-daemon/src/daemon/resident/execution.rs`, `execute_resident_wit_child`, `resident_watch_host_adapters`; `layer/core/what-is-mct.md`.]

**Proposed:** define graph edges as shared versioned WIT records, with explicit input digest and bounded output. Preserve the report's string/JSON v1 for compatibility, but do not claim it is already a typed report-to-report edge. The current report WIT only gives the runtime strings; application schema checking is inside the Child. [Basis: `crates/mct-repo-report/wit/world.wit`; `crates/mct-repo-report/src/lib.rs`, `ReportRequestV1`, `ReportV1`.]

Keep the four facts separate:

| Fact | Meaning in the canonical shape |
|---|---|
| `ComponentArtifact` | Immutable code/manifest identity, version, verified exports and provenance. Acquisition or possession is not permission. |
| `ChildApproval` | Local authority permits the exact artifact in scope. An upgrade is not silently covered by its old digest's approval. |
| `ChildAssignment` | Places that approved artifact in a Vision/Node/project scope. It does not mean a live ready process exists. |
| `ChildInstance` | The current runtime generation and readiness/lifecycle state. It is neither the package nor an owner identity. |

These are current ontology, not new proposal types. Replacement loads/verifies before draining the old generation. Persistence is less complete than the ontology: config still carries approval/assignment and peer records, and the open-questions document warns against claiming everything is reconstructible from the ledger. [Sources: `layer/core/what-is-mct.md`, “Child lifecycle”; `crates/mct-kernel/src/child.rs`; `crates/mct-daemon/src/config.rs:20–105`; `docs/OPEN-QUESTIONS.md` §4.]

## 2. Asking for Toys

A manifest `needs` entry requests a capability; it does not grant one. WIT imports declare what must be linked. An actual `ToyGrant` names exact Child/artifact/version, optional assignment/caller narrowing, Vision/node/project/data/resource/action scope, issuer, revisions and constraints. Kernel evaluation creates an `AuthorizedToyCall`; a serialized grant is not itself executable authority. [Sources: `layer/core/what-is-mct.md`, “The core inversion”; `crates/mct-kernel/src/toy.rs:1–100`.]

**Proposed workflow:** an author declares minimal needs; an operator reviews a readable grant proposal; Mother issues the exact bounded grant; the linker provides only admitted imports; effects recheck current authority. An application can request more power, never self-approve it. Treat future delegated handles as Mother-issued, attenuated and independently accounted for, not ordinary copyable strings. D-21/D-22 describe the courier model but explicitly mark that implementation unbuilt. [Basis: `docs/DECISIONS.md`, D-21/D-22; `crates/mct-daemon/src/daemon/resident/execution.rs`, `authorize_resident_toy`; `crates/mct-daemon/src/toy.rs`, effect admission methods.]

**Important built limit:** ordinary directory-read calls accept a strict import allowlist that excludes even logging. Generic keyvalue/messaging imports select the Watch adapter path and require a Watch scope. Do not have new apps import unused capabilities or fake Watch identities merely to reach storage. [Source: `crates/mct-daemon/src/daemon/resident/execution.rs`, `ordinary_directory_imports_supported`, `ordinary_directory_imports_are_strict`, `execute_resident_wit_child`.]

## 3. State and storage

Current invocation paths create fresh Wasmtime stores/instances. Treat memory as invocation-local, not durable app state. The current Child keyvalue adapter stores bounded key/value bytes in Mother's SQLite table, scoped by a bucket resource; it is not a Child-owned SQLite connection or generic SQL Toy. [Sources: `crates/mct-daemon/src/wasm.rs`, invocation methods and `MctWitKeyvalueHostAdapter`; `crates/mct-daemon/src/state.rs`, `child_keyvalue_get`, `child_keyvalue_set`; `crates/mct-daemon/src/daemon/watch.rs`, supporting keyvalue grant construction.]

**Proposed:** begin stateless, return a result, and let the application client retain it under a stable job ID. For later persistent Children, expose bounded Mother-owned keyspace operations, make writes idempotent by task/effect identity, and namespace state by Vision plus assignment rather than only an app nickname. Do not expose Mother's ledger/database files through a preopen. The first-app plan already separates durable client results from Mother's 12-minute dedupe window. [Basis: `docs/plans/first-real-app.md`, “Durable result”, final paragraphs; `crates/mct-daemon/src/state.rs`, `child_keyvalue_entries`; `crates/mct-daemon/src/daemon/watch.rs`, bucket resource construction.]

Do not sell persistent keyvalue as complete crash/replay semantics. D-28's ledger-backed session storage and self-wake Toy are rulings, not built Pi Durable functionality. D-30 describes replay-from-the-top, whereas the built restart contract settles interrupted calls and never resumes them. Child-start ordering and broader task/effect identity remain open. [Sources: `docs/DECISIONS.md`, D-28/D-30/D-32/D-40; `docs/OPEN-QUESTIONS.md` §§1,6,11.]

## 4. Delegation after #108

#108 proves one ordered two-piece job: arithmetic runs at A and repo-report runs at B; after B's directory-read grant expires, a fresh uncovered call is denied without runtime start. A records forwarding, B records its own execution, and correlation links the call IDs. It does not prove a durable graph scheduler, parallelism, restart-resume, automatic code transfer or multi-hop routing. [Source: `docs/nic63-mesh-job.md`, “Per-Mother ledger facts”, “Boundaries”.]

The implementation accepts 2–16 supplied pieces, derives per-piece call/idempotency IDs, then executes them sequentially through ordinary call law. It does not currently infer a graph from an arbitrary goal or wire one piece's output into another's input. [Source: `crates/mct-daemon/src/daemon/resident/local_ingress.rs`, constants, `local_job_protocol_requests`, and piece execution loop at lines 610–625.]

**Proposed:** keep splitting as an explicit bounded job description at the receiving Mother/application boundary. Each destination must already have the exact approved/assigned Child and its own local Toy/data grants. An offer is routing information, not authority; B independently admits and revalidates. Transfer immutable input references or explicitly authorized bytes, not A's memory or Toy handles. Keep D-37's terminal forwarded arrival; a cross-Vision bridge must not quietly become a second hop. [Basis: `docs/DECISIONS.md`, D-37/D-52; `crates/mct-daemon/src/daemon/resident/{candidates.rs,forwarding.rs,publication.rs}`; `docs/nic63-multi-host-plan.md`.]

# C. Vision for mine, someone else's, and shared Mothers

## 1. Separate the identities

**Proposed model:**

| Thing | What it means | What it must not imply |
|---|---|---|
| Owner/operator principal | A locally trusted administrator, established through explicit root registration and scoped admin authority. | Same owner does not mean shared endpoint keys, ledger, policy counter or automatic peer admission. |
| Mother/node identity | One sovereign execution/authority node and its transport endpoint identity. | Possession of an endpoint key is not admin permission. |
| Vision | A named sharing/data-policy boundary with an explicit issuer/governance policy. | Not necessarily a person, company, or a global security domain. A display name is not proof. |
| Membership | A locally accepted, expiring binding of a node/endpoint to a particular Vision context. | Membership is not permission to every operation, Toy, secret or admin route. |
| Cross-Vision grant | An explicitly approved directed sharing relationship for selected operations and data. | Not a union of memberships or transitive trust in every other peer. |

The separations are grounded in Vision's broader meaning, Iroh key possession versus MCT admission, D-58 administration and D-52's independent authorities. The many-Vision model itself is a proposal. [Sources: `layer/core/what-is-mct.md`, “Anatomy of a call”, “Vision”; `docs/DECISIONS.md`, D-52/D-58; `docs/passkey-admin.md`, “Current adapter”.]

**Proposed example:** my laptop Mother participates in Personal and Shared-Project; my worker Mother participates in Personal; another person's Mother participates in Their-Personal and Shared-Project. Each local assignment belongs to an explicit context. Shared-Project may expose a report operation without exposing either personal workspace. A call from Their-Personal directly into Personal is a different, explicitly granted cross-Vision relationship. Shared membership and cross-Vision access are not interchangeable.

## 2. What membership proves today

`MctPeerBinding` binds a peer endpoint to one MCT node and one Vision, with issuer, allowed ALPNs, revision, state and mandatory expiry. Hello checks observed endpoint possession against presented claims, selects a locally stored binding, and rejects revoked/expired/stale or wrong-Vision/ALPN claims. It is local admission evidence, not a universal owner certificate or a global group roster. [Sources: `crates/mct-kernel/src/peer/mod.rs:155–235`; `crates/mct-kernel/src/peer/internal.rs`, `evaluate_hello_internal`, `select_binding`.]

The daemon's bootstrap path creates receiver-issued proofs: the receiver signs with its local endpoint key; peers exchange those proofs for hello presentation. The signature covers issuer/peer node and endpoint identities, Vision, ALPNs, revision and expiry. A self-signed invitation from an unknown caller is not enough. Optional `data_scope` and `observation_scope` fields exist on the binding scope but are not included in the v1 signature payload; do not treat them as authenticated portable sharing grants. [Sources: `docs/nic63-multi-host-plan.md`, “Address and authority bootstrap today”; `crates/mct-daemon/src/config.rs`, `upsert_peer`, `set_peer_outbound_proof`; `crates/mct-iroh/src/identity.rs:90–176`; `crates/mct-kernel/src/peer/mod.rs`, `MctPeerBindingScope`.]

**Proposed membership flow:** an invitation describes the exact node/endpoint, Vision, expiry and requested surfaces. An authorized local administrator approves it. Mother durably records the binding and issues a proof; the caller proves endpoint possession and presents that receiver-issued proof. If a shared group later delegates enrollment to a membership issuer, each Mother must explicitly trust that issuer within a bounded scope and revocation policy. No central issuer is required for the first two-owner case.

## 3. Owner identity across my Mothers

D-58 uses a separately registered WebAuthn P-256 root tied to RP ID, origin, Mother and ledger. It issues scoped Ed25519 day-key leases for at most 24 hours. Commands bind the exact target/snapshot, nonce, scope and Mother time. Day keys cannot issue day keys, replace roots or extend themselves. Root or active KeyManage authority may revoke DayToDay grants. [Source: `docs/DECISIONS.md`, D-58; `docs/passkey-admin.md`, registration and issuance steps.]

**Proposed:** offer one owner-facing inventory of my Mothers, but enroll trust independently on each Mother. A passkey provider/account may make the human ceremony convenient; it does not make a lease for Mother A valid on B. Use separate target-bound leases and preferably separate day-key keypairs per Mother/task for compromise containment. Never clone a Mother's endpoint secret or canonical ledger to represent another node. These are proposed UX/key-management choices resting on D-58's existing target binding, not an implemented global owner identity.

There is a crucial integration gap: the passkey resident mode is admin-only; the legacy Child/Toy runtime refuses passkey ledgers. The current mesh evidence therefore does **not** prove D-58-governed Child/Toy administration. [Sources: `docs/passkey-admin.md`, “Current adapter”, “Resident Iroh key-management slice”; `docs/plans/first-real-app.md`, “Fleet map”; `docs/nic63-multi-host-plan.md`.]

D-53 brought guardian recovery into active design without making peers implicit guardians, authorizing work takeover, or specifying restoration of destroyed/compromised hosts. Its follow-through led to the older guardian/hybrid decisions, but D-58 now supersedes that ceremony for new administration. New-profile root rotation/recovery is not supplied merely by having several Mothers; the current passkey guide makes no root-rotation claim. [Sources: `docs/DECISIONS.md`, D-53, D-54–D-57 archive notice, D-58; `docs/passkey-admin.md`, limitations after the manual flow.]

**Proposed:** explicitly decide recovery for the passkey profile before promising “my other Mothers can recover me.” Appoint recovery-only guardians separately if Doug wants that feature; specify recovery authority, delay, cancellation, compromised-device exclusion and per-Mother commitment in a successor decision. Neither ordinary Vision membership nor an admin day key should confer root replacement.

D-45 is **commit attribution policy**, not owner identity or runtime trust. Its owner-only authorship rule must not be repurposed as an authorization design. [Source: `docs/DECISIONS.md`, D-45.]

## 4. How someone else's Mother joins or calls mine

**Proposed joining a shared Vision:** their operator retains control of their Mother. My administrator accepts its exact binding into Shared-Project on my Mother; their administrator reciprocates if bidirectional service is wanted. Publish only Shared-Project operations, not the Personal inventory. Each executing Mother still approves its local component, assignment and Toy use. Group membership gives no admin ALPN and no raw filesystem access.

**Proposed calling without joining my Vision:** keep their source Vision and my destination Vision explicit. My administrator grants one source principal/group permission to invoke one published operation on a destination assignment with input/output classifications, limits, expiry and audit-sharing policy. Their Mother must also permit sending those inputs. My Mother owns the local execution grants. No “pretend to be Personal” identity rewrite is allowed.

These extend, rather than describe, the current same-Vision implementation. D-37 requires a matching Vision, and current route candidates explicitly reject peer/surface Vision mismatches with the caller. Current hello publication also checks the admitted Vision against the published view. [Sources: `docs/DECISIONS.md`, D-37; `crates/mct-daemon/src/daemon/resident/candidates.rs:229–256`; `crates/mct-daemon/src/daemon/resident/publication.rs:45–111`.]

**Proposed checks for every cross-Vision call:** authenticated endpoint and valid local binding; explicit source/destination sharing grant; sender data-export approval; receiver call permission; exact artifact/assignment readiness; receiver Toy grants; result-release permission back to the caller. Each side ledgers its decisions. Denial remains caller-safe. Revocation of membership or the sharing relationship must block new admission even when a cached capability offer still exists. This preserves the authority-first/planning-second design rather than teaching the planner to bypass policy. [Basis: `layer/core/what-is-mct.md`, “Anatomy of a call”; `docs/DECISIONS.md`, D-36/D-37; `docs/nic63-post-review-suite.md`, receiver revocation checks.]

## 5. Cross-Vision grants that can scale

The repository records Kenton Varda's warning that manually configuring every agent's permissions means the approach has already lost; it also explicitly says only the opening of the post was read. It leaves scalable proposal/approval unresolved. Do not attribute a detailed solution to him. [Source: `docs/OPEN-QUESTIONS.md` §12.]

**Proposed answer:** approve intent and bounded policy templates once, materialize exact grants per assignment/task automatically under that approved ceiling. For example, “Shared-Project reviewers may inspect approved dependency snapshots, read-only, with bounded reports until this date.” The Child's manifest supplies requests, not the policy. Mother produces a reviewable delta and concrete grants with parent-template/provenance references. Those parent/template records are new design, not existing `ToyGrant` fields. [Basis for the gap and exact grants: `docs/OPEN-QUESTIONS.md` §12; `crates/mct-kernel/src/toy.rs`, `ToyGrant`, `ToyGrantSubject`.]

**Proposed scale rules:**

- Group operation grants by role, resource class and application version policy, not a hand-written all-to-all matrix for every Child/task.
- Preserve exact issued artifact/caller/resource grants underneath; an artifact upgrade outside the approved policy requires a new decision.
- Use local membership evaluation and short-lived task grants. Cache only with revision/expiry checks and fail closed when freshness cannot be established.
- Make parent revocation prevent new minting and invalidate descendants under an explicit in-flight policy. Do not promise instantaneous global cancellation during a partition.
- Keep broad administration and irreversible operations outside automatic low-risk templates unless Doug explicitly approves that scope.
- Keep discovery/advisory automation separate from authority issuance. A model can propose; it cannot grant.

The unsettled interaction between cascading revocation and already-admitted capabilities is a recorded open boundary; so is the decision-model Toy's status. The proposed scaling layer must settle those rather than hand-wave them away. [Sources: `docs/OPEN-QUESTIONS.md` §§8,11,12; `docs/DECISIONS.md`, D-21/D-26.]

### Tradeoffs

| Option | Benefit | Cost / recommendation |
|---|---|---|
| Put everyone in one Vision | Least immediate change under current D-52. | Cannot honestly model private versus shared groups. Reject as the target. |
| One separately deployed Mother per group | Uses the current one-Vision model and physical isolation. | Extra nodes/operations; not several Mothers pretending to be one deployable node. Useful temporary deployment choice, not multi-membership. |
| One Mother, multiple explicit memberships | Matches personal/shared membership without duplicating node identity. | Requires the scope/index/publication changes above. **Recommended target.** |
| Cross-Vision import of selected operations | Cooperation without full group membership. | New policy/wire/revocation work. Add after multi-membership isolation, not by removing equality checks. |

The first two options are constrained by the current one-Mother-per-node and one-local-Vision contract; the last two are proposals. [Sources: `layer/core/what-is-mct.md`; `docs/DECISIONS.md`, D-52.]
